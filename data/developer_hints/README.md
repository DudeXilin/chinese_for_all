# Developer hints

Эта папка хранит подсказки разработчика для слов и отдельных иероглифов.

## Как устроена система

У приложения есть единое пространство ключей `itemKey`. Ключом может быть:

- один иероглиф: `我`, `个`, `学`;
- целое слово: `你好`, `学生`, `电脑`.

Подсказка выбирается в таком порядке:

1. **Личная подсказка пользователя** — хранится в Supabase и видна только этому пользователю.
2. **Подсказка разработчика** — хранится в этой папке GitHub и является общей для всех пользователей.
3. **Этимологическая подсказка Make Me a Hanzi** — используется для отдельного иероглифа, если пользовательская и developer-подсказки отсутствуют.
4. Если ничего нет — подсказка отсутствует.

### Личные подсказки

Пользователь может нажать на подсказку в интерфейсе и сохранить собственный вариант.

Личные подсказки хранятся в таблице Supabase:

`public.user_hints`

Ключ таблицы — пара `(user_id, item_key)`. Row Level Security ограничивает доступ так, чтобы пользователь мог читать и изменять только свои записи.

Личные подсказки **не хранятся в GitHub**.

Если пользователь удаляет свою личную подсказку, приложение снова использует developer-подсказку, Make Me a Hanzi или отсутствие подсказки в зависимости от доступных данных.

### Подсказки разработчика

Developer-подсказки хранятся в шардированных JSON-файлах:

`data/developer_hints/00.json` ... `data/developer_hints/FF.json`

Шард определяется функцией `lib/hints/sharding.ts`. Это позволяет не складывать все подсказки в один огромный файл.

Пример содержимого JSON:

```json
{
  "个": "Летящая птичка",
  "我": "Представь себя с копьём",
  "你好": "Два человека приветствуют друг друга"
}
```

Обычным пользователям эти подсказки доступны для чтения через приложение, но редактировать их они не могут.

## Как работает редактирование developer-подсказки

Администратор редактирует подсказку через интерфейс сайта.

Запрос идёт в:

`POST /api/hints`

с режимом:

`mode: "developer"`

Сервер проверяет:

1. пользователь авторизован в Supabase;
2. его Supabase user ID совпадает с серверной переменной окружения `ADMIN_USER_ID`;
3. на сервере существует `GITHUB_TOKEN`.

После этого сервер:

1. определяет нужный shard;
2. получает текущий JSON из GitHub;
3. изменяет только нужный `itemKey`;
4. создаёт commit в ветке `main`.

### Почему подсказка появляется почти сразу

GET-запрос `/api/hints` больше не читает developer-подсказки из локального файла, который был создан во время Vercel build.

Вместо этого сервер получает актуальный shard непосредственно из GitHub.

Поэтому после сохранения:

**сайт → GitHub → новый commit → следующий запрос сайта видит новую подсказку**

и отдельный Vercel deployment для каждой подсказки не требуется.

Кроме того, в настройках Vercel используется Ignore Build Step, который пропускает deployment, если commit изменяет только файлы внутри `data/developer_hints/`.

Это важно: изменения самого приложения по-прежнему должны запускать обычный Vercel deployment.

**Важно при настройке Ignore Build Step в Vercel:**
- Не полагайтесь на сравнение с предыдущим SHA без обработки ошибок: Vercel может не иметь этот commit в локальном Git-клоне, и `git diff` завершится с ошибкой вроде `fatal: bad object`.
- Логика должна пропускать сборку только когда успешно подтверждено, что изменились исключительно файлы `data/developer_hints/`.
- Если сравнение Git не удалось или предыдущий SHA недоступен, безопасное поведение — **продолжить сборку**, а не пропускать её.
- После изменения команды Ignore Build Step проверьте новый deployment в Vercel.

## Как будущему разработчику получить права администратора

Администратор определяется **не по имени, email или GitHub-аккаунту**, а по Supabase user ID.

Чтобы выдать права своему аккаунту:

1. Создайте обычный аккаунт через интерфейс приложения **(например, `вашсайт.com/register`)**.
2. В Supabase Dashboard найдите пользователя в Authentication → Users.
3. Скопируйте его **User UID**.
4. В настройках Vercel проекта добавьте/измените серверную переменную:

`ADMIN_USER_ID=<ваш Supabase User UID>`

Переменная должна существовать для тех окружений, в которых вы хотите администрировать приложение (обычно Production, Preview и Development).

5. Создайте GitHub token, который сервер сможет использовать для чтения и изменения developer-подсказок.
6. Добавьте этот token в Vercel:
   - откройте **Vercel Dashboard**;
   - выберите проект;
   - откройте **Settings → Environment Variables**;
   - создайте переменную **`GITHUB_TOKEN`**;
   - вставьте token в поле **Value**;
   - включите **Production**, **Preview** и **Development**, если хотите, чтобы администрирование работало во всех этих окружениях;
   - сохраните переменную как **Sensitive/Secret** (если такой выбор доступен).
7. Убедитесь, что GitHub token имеет необходимые права для чтения и записи содержимого репозитория `DudeXilin/chinese_for_all`. Для fine-grained token выдайте доступ именно этому репозиторию и разрешение **Contents: Read and write**.
8. Перезапустите/redeploy приложение, чтобы новые значения переменных окружения стали доступны server-side.
9. Войдите в приложение под этим Supabase аккаунтом.

После этого компонент подсказок получит признак администратора, и для вас станет доступно редактирование developer-подсказки.

### Критически важно: не публикуйте свой UID без необходимости

Сам по себе Supabase User UID не является паролем, однако это персональный идентификатор аккаунта. Не добавляйте его в:

- исходный код;
- `.env` файлы, которые коммитятся;
- JSON-файлы в `data/`;
- README;
- GitHub Issues/PR;
- client-side JavaScript;
- публичные логи.

`ADMIN_USER_ID` должен оставаться **server-side переменной окружения Vercel**.

В репозитории должен находиться только код, который обращается к:

`process.env.ADMIN_USER_ID`

а не конкретное значение UID.

## Как не слить секреты в GitHub

Для администрирования подсказок также нужен:

`GITHUB_TOKEN`

Это секрет. Его нельзя помещать в GitHub.

**Никогда не делайте так:**

```ts
const GITHUB_TOKEN = "ghp_...";
```

и не добавляйте токен в:

- `.env`, если этот файл отслеживается Git;
- README;
- исходный код;
- JSON;
- клиентский JavaScript;
- commit message;
- screenshots;
- публичные Issues/PR.

Токен должен храниться только в серверном окружении Vercel как Secret/Encrypted environment variable.

Код использует его через:

`process.env.GITHUB_TOKEN`

Браузер пользователя не должен получать значение этого токена.

Также не копируйте в репозиторий содержимое Vercel/Supabase environment variables. Если секрет случайно попал в GitHub, его нужно считать скомпрометированным и немедленно заменить/revoke.

## Важное правило для будущих разработчиков

Если вам нужно дать себе права администратора, **не изменяйте код ради этого**.

Не добавляйте:

```ts
if (email === "my@email.com") ...
```

или:

```ts
const ADMIN_USER_ID = "ваш-uid";
```

Вместо этого используйте Vercel Environment Variables:

- `ADMIN_USER_ID` — ваш Supabase User UID;
- `GITHUB_TOKEN` — GitHub token с необходимыми правами.

Таким образом, личные данные и секреты остаются вне публичного GitHub-репозитория.

## Где искать код системы

Основные файлы:

- `app/api/hints/route.ts` — API чтения и сохранения подсказок;
- `components/hint.tsx` — интерфейс подсказки и редактора;
- `lib/hints/sharding.ts` — определение shard;
- `supabase/hints-schema.sql` — схема таблицы пользовательских подсказок;
- `data/developer_hints/*.json` — публичные developer-подсказки.

При изменении этой системы особенно важно сохранять разделение:

**Supabase → личные данные пользователей**

**GitHub → публичные developer-подсказки и код**

**Vercel Environment Variables → секреты и идентификаторы, которые не должны попадать в GitHub**

## Безопасность

Developer-подсказки являются публичными данными по дизайну. Не помещайте сюда пароли, API keys, access tokens, email-адреса, UID пользователей или другую приватную информацию.

Эта папка предназначена только для учебных подсказок, которые разрешено видеть всем пользователям приложения.
